# Modelo de amenazas

Estado: Activo · **Fase 6 · actualizado 2026-07-07** · Revisión obligatoria ante cambios de superficie y antes de abrir el sandbox compartido (PEND-006) / integrar el proveedor real (Fase 5).

> **Qué cambió respecto a la versión Fase 0.** Aquella era un plan («Diseñado/Parcial»); esta refleja lo **implementado y verificado** tras las Fases 1–4 y las dos auditorías independientes (v1 + re-auditoría v2, ambas remediadas — `docs/audits/`). Cada control se ancla en código/migración/test concretos, con su forma de verificación. El §5 es el **backlog de endurecimiento de la Fase 6** derivado de este análisis (riesgo residual real, priorizado). Método: STRIDE por frontera de confianza. Inventario base: 89 controles + 34 riesgos residuales relevados con evidencia (subsistemas: aislamiento multi-tenant, integridad del ledger, idempotencia/concurrencia, authn/authz, webhooks/SSRF, secretos/datos/cadena de suministro).

Alcance: sandbox, sin dinero real ni datos de tarjeta reales. Aun así el modelo se construye como si fueran reales — los controles Nivel A son los mismos que exigirá producción. La exposición pública de la API de pagos/checkout/webhooks y todo uso `live` siguen **congelados** (decisión #24) hasta re-auditoría + PEND-006.

## 1. Contexto, actores y fronteras de confianza

Monolito modular (`system-overview.md`): `apps/api` (Fastify) + frontends Next.js (dashboard, checkout, admin) que importan paquetes de dominio (sin HTTP interno); `apps/worker` corre relay/jobs y hace las ÚNICAS llamadas de red salientes (webhooks, proveedor); PostgreSQL 16 es la fuente de verdad; Redis es cache/coordinación (jamás fuente duradera).

| Actor / entrada                | Frontera cruzada                                     | Credencial                               | Confianza                                          |
| ------------------------------ | ---------------------------------------------------- | ---------------------------------------- | -------------------------------------------------- |
| Integrador (API key)           | Internet → `apps/api` `/v1`                          | `fluvia_sk_*` (Bearer, HMAC server-side) | No confiable; scoped por tenant+permiso            |
| Comprador (checkout)           | Internet → `/v1/checkout_sessions/:id/*` sin API key | `client_secret` `cs_` (en el fragment)   | No confiable; solo su sesión                       |
| Operador (dashboard/admin)     | Internet → sesión + membresía                        | Cookie httpOnly `fluvia_session` + RBAC  | Semi-confiable; RBAC + four-eyes                   |
| Proveedor (webhooks entrantes) | Proveedor → inbox `/v1/providers/mock/webhook`       | HMAC del proveedor                       | No confiable hasta verificar firma                 |
| Endpoints de webhook salientes | `apps/worker` → Internet                             | — (nosotros firmamos)                    | **Superficie SSRF**: destino potencialmente hostil |
| DBA / superusuario / infra     | Fuera del proceso                                    | Acceso a cluster/secret manager          | **Tier de confianza superior** (ver §4)            |

Fronteras duras de runtime (`system-overview.md` §3): ninguna llamada de red dentro de una tx SQL (outbox/inbox es el único puente); todo dato externo pasa por Zod en el borde; contexto de tenant solo por `set_config(...,local)` en tx; dinero solo como `Money` (bigint); estados de FSM solo mutables por su servicio de dominio.

## 2. Activos

Fondos contables (ledger append-only + proyecciones), credenciales (API keys, sesiones, secretos de webhook, seed TOTP, futuras credenciales de proveedor), PII de customers, integridad y no-repudio de eventos y del `audit_log`, disponibilidad del pipeline de pagos, y la confianza/reputación de la plataforma.

## 4. Supuestos de confianza (tiers)

- **Tier runtime (modelado a fondo)**: los roles `fluvia_app/worker/relay/inbox/auth/webhook` — sin BYPASSRLS, mínimo privilegio, RLS forzado. Es la superficie principal del modelo.
- **Tier DBA / superusuario / infraestructura (confianza superior, explícito)**: el superusuario de PG puede saltar triggers/constraints vía `session_replication_role` y leer todo; la infra (secret manager, red) es de confianza. En Fases 1–4 (local/CI) queda fuera del alcance activo; **en Fase 6/producción entra** con secret manager, acceso mínimo, y —como tamper-evidence opcional— archivado append-only/hash-chain de `ledger_entries` (ver §5).
- **MockProvider**: es código propio pero NO se le confía distinto — pasa por el MISMO inbox verificado (firma + dedup), así el pipeline queda probado como si fuera externo.
- **Congelado por decisión**: exposición pública y `live` bloqueados (decisión #24) hasta re-auditoría + PEND-006; payouts reales bloqueados por diseño en el MVP.

## 6. Verificación y mantenimiento del modelo

- **El modelo se mantiene honesto por prueba, no por afirmación**: cada control del §3 cita test/CI/drill; los invariantes del ledger corren en CI (`verify-ledger-invariants.sql`) y en el drill de restore; los meta-tests estructurales en `pg_catalog` cubren tablas y roles FUTUROS (una tabla nueva sin RLS, o un rol nuevo con BYPASSRLS/DELETE, rompe el build).
- **Dos auditorías independientes** (v1 + re-auditoría v2) están integradas y remediadas (`docs/audits/audit-closure-register-v1.md`: 0 P1 / 0 P2 abiertos); sus hallazgos son entradas de este modelo.
- **Disparadores de revisión**: nuevo endpoint mutante de dinero, nuevo rol/tabla, integración del proveedor real (F5), apertura del sandbox compartido (PEND-006), o cualquier hallazgo de auditoría. Los ítems del §5 se rastrean como backlog de Fase 6 con evidencia por cierre.
- **Correcciones sancionadas** (nunca SQL manual sobre dinero): compensación/ajuste con caso + four-eyes, replay auditado de outbox/inbox, rebuild explícito de proyecciones (`incident-response.md`, `runbooks/`).
